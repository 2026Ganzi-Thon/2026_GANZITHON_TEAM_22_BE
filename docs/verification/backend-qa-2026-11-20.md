# 11월 20일 백엔드 QA

합성 계정, 격리한 MySQL, 로컬 Spring 서버로 확인했다. 계약은 [OpenAPI](../implemented.openapi.json)에 있다. 아래 재시도와 버전 처리는 지원하는 클라이언트에서 적용된다.

| 사용자 상황 | 서버와 프론트의 계약 |
|---|---|
| 할 일·세부 할 일 저장 직후 응답 유실 | 같은 작성 건은 같은 `clientRequestId`와 본문으로 재전송한다. 첫 생성은 201, 동일 요청은 200과 같은 항목 ID다. 사용자가 같은 제목으로 새 항목을 추가하면 새 ID를 사용한다. 삭제 뒤의 옛 요청은 409로 끝난다. |
| 두 기기가 한 할 일을 편집 | 편집 당시의 `expectedVersion`과 실제 수정 필드를 보낸다. 409 `TASK_VERSION_CONFLICT`이면 상세를 다시 읽어 미저장 입력과 비교한다. 제목과 마감일처럼 겹치지 않는 수정은 새 버전으로 적용하고 같은 필드의 충돌은 사용자에게 보여준다. 버전은 부모 할 일 필드에 적용된다. |
| 같은 DB에서 두 서버가 순차적으로 대화 처리 | 같은 사용자와 같은 대화방의 최신 저장 턴만 `previousRequestId`로 인정한다. 오래된 턴을 지정하면 새 모델 호출 없이 409를 반환한다. 두 서버에서 정확히 동시에 시작되는 대화의 직렬화는 별도 검증 대상이다. |
| 같은 할 일을 짧게 여러 번 공부 | 할 일 누적은 `totalTaskStudySeconds`를 쓴다. 0.6초씩 두 번이면 1초다. 무연결 공부에서는 이 값이 `null`이고 이번 공부 시간은 `studySeconds`다. |

구형 앱이 생성 ID나 편집 버전을 생략하면 예전 방식으로 동작한다. 응답 유실 뒤 중복 추가와 오래된 값 덮어쓰기를 막으려면 프론트가 두 필드를 사용해야 한다.

## 재현

Java 21·Node.js·MySQL 8을 설치한 Windows에서 저장소 루트의 `node scripts/verify-local.mjs`와 `node --test scripts/public-preflight.test.mjs`를 실행한다. 전자는 무작위 포트의 임시 DB로 자동시험, HTTP, 재시작 복구, 배포 프로필과 스키마 일치를 확인한다. 후자는 배포 점검 도구의 오류 인식과 응답 재조회를 모의 제공자로 시험한다.

최종 실행에서 자동시험 247개(35개 묶음)가 통과했고 실패·오류·건너뜀은 0개였다. 실제 로컬 HTTP로 OpenAPI 연산 33개를 모두 호출해 시나리오 26개를 통과했다. 배포 설정 HTTP 요청 18건과 배포 점검 도구 모의시험 9건도 통과했다. V1~V8 적용 결과와 빈 개발 DB가 테이블 16개, 열 137개, 인덱스 항목 98개, 외래 키 16개, 검사 제약 38개에서 일치했다.

초기 실행에서는 할 일 버전 열의 위치와 기존 상태 제약의 문자셋이 두 DB에서 다르게 기록됐다. 독립 생성 SQL을 V8 적용 결과에 맞춘 뒤 전체 시험을 다시 수행했다. 위 결과는 최종 소스 기준이다.

별도 사본에서 앞서 차이를 발견했던 시나리오를 다시 실행했다. 생성 응답 유실, 두 기기 편집, 게스트→회원 전환 후 재시작 등 실제 HTTP 5건과 채팅 직전 턴·누적 시간·알림 경계 등 독립 JUnit 6건이 통과했다. 변경 전에는 11건 중 6건이 기대와 일치했다. 이번 11건은 새 요청 필드와 응답값을 사용하는 경로이며, JUnit 집계 253개에는 기존 247개가 포함된다.

## 리뷰 후 배포 확인

Flyway V6은 푸시 기기를 로그인 세션과 연결하고, V7은 할 일 생성 요청 기록을 추가하고, V8은 기존 할 일의 편집 버전을 0으로 초기화한다. AWS QA에 반영한 뒤 일반 대화와 스터디룸 각각에서 새 응답을 받고 같은 요청 ID로 저장 답변을 다시 읽는다. 제출 APK에서는 두 기기의 계정 전환, 잠금 화면의 5분 이탈 알림과 다음 시작 예약 알림을 각각 확인한다.
