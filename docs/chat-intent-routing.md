# 캐릭터 대화 의도 분류

먼저 답할 캐릭터를 고른 뒤, 해당 캐릭터의 프롬프트로 대사를 생성한다. 11월 9일 회의에서 제안했고 11월 10일 백엔드 협의 후 기본 대화 흐름에 적용했다. [11월 9일 팀 회의록](https://app.notion.com/p/2026-11-09-413514692619807f9ef7e2b164805665)

서버는 현재 메시지와 `characterKeys` 후보로 응답 범위를 고른다. 후보가 한 명이면 그 친구의 프롬프트를 쓴다. 여러 명 중 문장 처음에 한 캐릭터만 명확히 부르면 그 친구를 고른다. 여러 친구나 모두를 부르거나, 부른 친구가 후보에 없으면 그룹 프롬프트를 쓴다. 호명이 없으면 규칙에 맞는 짧은 감정 표현이나 함께 공부를 시작하자는 제안에서 후보를 좁힌다. 감정이 섞이거나 뜻이 모호하면 그룹 프롬프트를 쓴다. 예전 메시지는 대사 생성에 필요한 문맥으로 쓴다.

| 입력 예시 | 모든 캐릭터가 후보일 때 |
| --- | --- |
| 슬픔아, 잠깐 얘기할래? | 슬픔이 전용 프롬프트 |
| 안녕 기쁨아 | 기쁨이 전용 프롬프트 |
| 슬픔아ㅠㅠ | 슬픔이 전용 프롬프트 |
| 화남아, 같이 들어줄래? | 화남이 전용 프롬프트 |
| 오늘 정말 속상해. | 슬픔이 전용 프롬프트 |
| 우리 같이 공부 시작하자! | 기쁨이 전용 프롬프트 |
| 합격했는데 속상해. | 기존 그룹 프롬프트 |
| 화남아, 다들 어떻게 생각해? | 기존 그룹 프롬프트 |
| 오늘 하루가 좀 복잡했어. | 기존 그룹 프롬프트 |

서버 내부 규칙으로 화자를 선택하고, OpenAI 연결을 사용해 한 턴에 최대 한 번 대사를 생성한다. 기본 모델은 `gpt-6.1-sol`, 추론 설정은 Standard `medium`, 출력 상한은 2,048토큰이다. 이 상한에는 추론 토큰이 포함된다. 예산 예약과 실제 호출은 같은 프롬프트 및 후보를 사용한다. [GPT-6.1 Sol 모델 설명](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 연동과 시험

- `POST /api/v1/chat/exchanges`에서 `characterKeys`는 답변 후보 목록이다. 생략하면 세 캐릭터가 후보가 된다. 특정 캐릭터와 대화하는 화면은 해당 키 하나를 보낸다. 프론트는 `utterances[]`의 실제 `characterKey`와 순서에 따라 말풍선을 그린다.
- AI 대화가 설정된 환경에서 의도 분류가 기본 동작한다. 비교가 필요하면 시험 환경에서 `GANZI_CHAT_INTENT_ROUTING_ENABLED=false`로 설정한 뒤 서버를 재시작한다. 새 요청에는 그룹 프롬프트를 사용하고 이전 요청은 저장된 답변을 반환한다.
- 서버에 포함된 시연 화면은 세 캐릭터를 처음부터 후보로 선택한다. “슬픔아, 잠깐 얘기할래?”를 보내면 슬픔이 응답을 확인할 수 있다.
- 같은 합성 입력으로 두 설정을 비교할 때 새 `clientRequestId`를 쓴다. 동일 ID는 저장된 결과를 재생하므로 방식 비교에는 적합하지 않다. 호명·혼합 감정·전체 호출·공부 중 대화·지난 대화 언급을 각각 확인하고, 어울리는 화자와 말투인지, 응답 시간, 입력·출력 토큰, 실제 추정 비용을 기록한다. 대화 원문을 별도 운영 로그로 남길 필요는 없다.
- 다른 지원 모델을 Thinking `medium`으로 시험할 때는 `GANZI_OPENAI_MODEL`과 `GANZI_OPENAI_REASONING_EFFORT=medium`을 함께 지정한다. Sol 기본값은 `medium`이고, Luna·Terra의 기존 배포 기본값은 `none`이다.

## 응답 대기와 복구

앱의 대화 요청 제한 시간은 기본 서버 응답 마감 30초에 네트워크 여유를 더해 **35초 이상**으로 설정한다. 진행 중에는 답변 대기 상태를 표시하고, 사용자가 같은 메시지를 반복해서 보내지 않도록 한다. 운영에서 서버 마감이 달라지면 앱과 중간 프록시의 제한 시간도 함께 확인한다.

| 받은 결과 | 앱 처리 |
| --- | --- |
| 연결 끊김·타임아웃 또는 `409 REQUEST_IN_PROGRESS` | 기존 `clientRequestId`와 원래 본문을 보존한다. `GET /api/v1/chat/exchanges?clientRequestId=...`로 약 4초 간격으로 조회한다. 35초 정도 지나면 자동 조회를 멈추고 사용자가 다시 확인할 수 있게 한다. 서버에 다시 전송할 때 같은 ID와 본문을 쓴다. |
| 조회에 `PROCESSING` 또는 `items: []` | 아직 확인된 결과가 없다. 빈 결과를 전송 실패로 확정하거나 새 ID로 자동 재전송하지 않는다. |
| `200 SUCCEEDED` 또는 `200 FAILED` | 해당 시도의 완료 결과로 처리한다. `FAILED`는 `failureCode`를 읽는다. 새 요청은 사용자가 명시적으로 다시 보낼 때만 만든다. |
| `503 CHAT_HISTORY_UNAVAILABLE` | `retryable: false`이면 손상된 저장 결과이므로 같은 ID에 대한 재조회를 중단한다. `true`이면 조회 오류이므로 기존 ID를 보존하고 다시 확인할 수 있다. |
| `409 INVALID_PREVIOUS_EXCHANGE` | 거절된 전송의 내용을 입력창에 보존하고, 직전 대화 연결을 지운다. 사용자가 다시 보내면 새 `clientRequestId`를 만들고 `previousRequestId`를 생략한다. 서버가 고른 사용자 기록은 문맥에 쓰일 수 있다. |

결과 저장 또는 정산에 실패하면 이미 사용된 모델 호출의 재실행을 막기 위해 예약이 남을 수 있다. 그동안 같은 요청의 POST가 `REQUEST_IN_PROGRESS`를 반환할 수 있고, 저장된 결과 없이 예약이 끝나면 `200 FAILED CHAT_RESULT_UNAVAILABLE`로 종료된다. 이 경로도 같은 ID로 복구하고, 자동으로 새 유료 요청을 만들지 않는다.
